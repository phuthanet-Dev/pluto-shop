# Phuto Shop Admin Redesign Implementation Plan

> **For Hermes:** Implement task-by-task with isolated subagents where available; load Impeccable, test-driven-development, frontend-ui-regression, and requesting-code-review before their relevant stages. Review specification compliance before code quality. This document is a plan, not authorization to deploy or modify production.

**Goal:** ทำให้ผู้ดูแล Phuto Shop ค้นหา เพิ่ม แก้ไขสินค้า และจัดการการส่งมอบได้โดยเห็นเฉพาะสิ่งที่เกี่ยวกับงานตรงหน้า เข้าใจข้อความภาษาไทย และไม่สูญเสียข้อมูลหรือความปลอดภัยเดิม

**Architecture:** Keep the existing server-protected `/admin` route and existing BFF/API contracts; introduce a small client workspace that selects products or fulfillment rather than rendering both consoles together. Keep each console's mutation/state ownership intact initially, then progressively disclose form sections and option editors without rewriting serialization, optimistic concurrency, inventory encryption, or payment logic. Scope the new operational visual system to `.admin-workspace` so the public marketplace remains unchanged.

**Tech Stack:** Next.js App Router, React, TypeScript, existing custom controls and Radix-backed FeedbackDialog, CSS, Vitest/Testing Library, Playwright. No new package required.

### Product truth to retain

- Display brand is `SITE_BRAND_DISPLAY = "Phuto Shop"` in `apps/web/lib/brand.ts`; technical `SITE_BRAND = "phutoshop"` is separate.
- Thai is the admin UI language; TH/EN **product content** remains required where currently required. Do not auto-translate, silently copy Thai into English, or make required English fields optional.
- Create defaults currently include ACTIVE, INSTANT, stock 0, warranty 0, warning threshold 5. Do not change these business defaults under a visual redesign.
- `SINGLE_OPTION` and `MULTI_OPTION` are selection modes, not bundle/product-type aliases. Keep IDs, slugs, optionGroup, per-child version and group version exactly.
- Multi create uses an atomic API and currently requires at least two child records, maximum 100. Group append and one-child edit have different rules; do not unify their writes.
- Image upload is a separate versioned operation available after product creation, JPEG/PNG up to 5 MiB, server validation authoritative. Do not imply that Cancel undoes a completed image upload.
- Catalog stock is not synonymous with ready-to-deliver encrypted inventory. Never synchronize them client-side or label them as one total.

## 2. Assumptions, scope and exclusions

Assumption: primary operator is the maintainer managing products on desktop, with mobile support for occasional work. The first release covers current admin capabilities only, not a new order/payment management system.

**In scope:** task navigation, list readability, focused editor, progressive disclosure, Thai copy, responsive layout, keyboard/focus, unsaved changes, error placement, safer fulfillment identity/navigation and secret-state cleanup.

**Out of scope:** changing API/database schema, auth, roles, payment flow, deleting data, new analytics, bulk delete, order list API, autosave, cloud draft persistence, new image pipeline, search provider, framework migration, public storefront redesign, production deployment. No fake revenue/order cards or placeholder navigation.

Default direction for approval: keep the store's dark neutral + restrained violet identity and LINE Seed Sans, but replace the admin composition. This is an operational tool, not a marketing landing page. No hero, gradient text, orbital art, animated entrance, decorative dashboard charts, or glass panel stacks.

## 3. Concrete UX specification

### 3.1 Information architecture

Use the existing `/admin` URL. Do not add routes/query-string draft state in release one.

```
Phuto Shop · หลังบ้าน                 ไปหน้าร้าน | ออกจากระบบ
[สินค้า] [การส่งมอบ]                  ← task navigation, not ARIA tabs

สินค้า                               [+ เพิ่มสินค้า]
ค้นหาสินค้า [ชื่อ / รหัส URL ...] [ค้นหา] [ล้าง]
รายการสินค้าที่โหลดมา                 โหลดใหม่
สินค้า | ราคา (บาท) | สต็อกสินค้า | การส่งมอบ | สถานะ | จัดการ
...
```

Use nav buttons with `aria-pressed`, not a partly implemented tablist. Active console only is mounted. Switching while dirty asks first; switching while saving/importing/revealing is blocked. Changing sections unmounts fulfillment secret state. The selected section is in memory only; reload returns to products. This intentional simplicity must be documented, not disguised as deep-link support.

List rows remain one SKU/child each in release one; do not invent group-wide aggregate prices/stock from partial search results. Display child option label adjacent to name and optionGroup as muted technical metadata. All mutation targets remain exact IDs. Visible action text: `แก้ไข`, `เพิ่มตัวเลือก`, `แก้ไขข้อมูลกลุ่ม`; destructive action is in editor `การดำเนินการถาวร`, not an adjacent unlabeled trash icon. Accessible names add product name AND ID to distinguish repeated child names; update tests accordingly.

No decorative KPI cards. List count must say `แสดง N รายการ` computed from the displayed collection; do not call it catalog total unless the API total contract has been checked.

### 3.2 Focused product editor

Opening create/edit/group-edit/group-append replaces the table/search area with editor workspace; do not render two active tasks. Keep the outer list state in AdminProductsConsole so returning preserves submitted query. No modal for the main editor.

Header: `กลับไปรายการสินค้า`, context-aware title, current item/group identity. Exactly one primary submit action at the bottom in a sticky, in-flow footer. `ยกเลิก` is secondary. Pending mutation disables navigation and submit. Success returns to list and announces status; failure preserves values.

Titles: create `เพิ่มสินค้า`; single edit `แก้ไขสินค้า`; multi child edit `แก้ไขตัวเลือก`; group edit `แก้ไขข้อมูลกลุ่ม`; append `เพิ่มตัวเลือกในกลุ่ม`.

Single product form order:
1. `ข้อมูลสินค้า`: Thai/English names, short summaries, descriptions. Language labels are explicit; both languages visible initially, not hidden behind a tab that can conceal required errors.
2. `ราคาและการขาย`: price in baht, catalog stock, delivery dropdown, sale status dropdown.
3. `รายละเอียดเพิ่มเติม`: collapsible warranty, warning threshold, sort order. These optional-to-view fields retain their current values/defaults.
4. `รหัสและการจัดกลุ่ม`: slug always discoverable; keep slug visible in CREATE because it is required. In EDIT it can live in a disclosure with helper `รหัสนี้ใช้ระบุสินค้า การแก้ไขอาจกระทบลิงก์เดิม`. Do not auto-regenerate existing slugs.
5. `รูปสินค้า`: existing upload interaction; create states exactly that the product must first be saved. Helper explicitly says upload saves separately.
6. `การดำเนินการถาวร`: collapsed delete section, existing product only, existing irreversible-effect confirmation retained.

Multi product order: selection mode and optionGroup → shared card names/summaries → child summaries/editors → optional details → save. Replace the incumbent detached shared-data sidebar; shared data comes first in normal document flow. Copy `ข้อมูลบน Product Card` becomes `ข้อมูลที่แสดงบนหน้าร้าน`; `SHARED` becomes `ใช้ร่วมกันทุกตัวเลือก`; technical values may appear in helper text, not as the main heading.

Child list uses disclosure summaries (`ตัวเลือกที่ 1 · <label or ยังไม่ตั้งชื่อ> · <price>`) with only the first open initially. Add child opens/focuses the new child. Collapse never discards React state. Use stable client-only keys for new child drafts; never index identity when removing drafts. Changing MULTI to SINGLE while populated extra drafts exist requires discard confirmation. Error opens the owning child and section before focusing the invalid field. Required hidden fields must not cause browser `invalid form control not focusable` errors: use form `noValidate`, explicit existing validation plus field targeting, then server validation as final authority.

### 3.3 Fulfillment

Separate from product editing. Initially show product selector/ID fallback and a collapsed `เครื่องมือแก้ปัญหาการส่งมอบ`. Label `รหัสสินค้า/child` as `รหัสสินค้า (SKU)` with explanation; phase one may retain ID input but list/editor adds `จัดการการส่งมอบ` for an existing SKU to hand off exact ID and display name. No fake global order selector without a supporting API.

After loading a product show immutable heading `การส่งมอบ: <name> · SKU #<id>`. Separate `รหัสที่กำลังค้นหา` from `loadedProductId`; mutation functions must use the successfully loaded ID only. On changing selection, clear stale profile/inventory/reveals and disable mutations until loading succeeds. Discard out-of-order reads with an epoch ref. This is a security prerequisite, not optional visual polish.

Sections: `รูปแบบและขั้นตอนส่งมอบ`, `คลังข้อมูลส่งมอบ`, `เพิ่มข้อมูลส่งมอบ`. Within add section, choose one-at-a-time or batch; don't expose both secret forms simultaneously. Collapse/unmount of secret editor or changing SKU clears password/key/batch/revealed values after dirty confirmation; do not keep secrets merely hidden in DOM. Inventory list exposes metadata/status only until explicit reveal with existing reason enum. All available actions remain reachable, but revoke/quarantine/manual-ready/retry get a confirmation naming exact target and effect. Never automatically reveal/copy or infer paid state from frontend data.

Known state handling to test: async reveal resolving after SKU change must be ignored; failed load must not leave prior SKU actionable; save/import pending blocks navigation; changing draft fulfillment type does not silently rewrite existing inventory or payload schema.

Copy map (API enum unchanged): `PROFILE` → `การตั้งค่าการส่งมอบ`; `Provider` → `ผู้ให้บริการ`; `Customer steps / Operator steps` → `ขั้นตอนสำหรับลูกค้าและผู้ดูแล`; `บันทึก profile` → `บันทึกการส่งมอบ`; `เพิ่ม inventory` → `เพิ่มข้อมูลส่งมอบ`; `นำเข้าแบบ batch` → `นำเข้าหลายรายการ`; `รายการ inventory` → `คลังข้อมูลส่งมอบ`; `CUSTOMER` → `ลูกค้า`; `OPERATOR` → `ผู้ดูแล`. Preserve distinction between sale status and inventory status in all badges.

### 3.4 Visual and interaction contract

- Desktop >=1024: max content width 1280px, page padding 32px, compact header and horizontal task navigation. No sidebar needed for two sections.
- Tablet 768–1023: padding 24px; form remains at most two columns where labels fit.
- Mobile <768: padding 16px; single-column fields; wrap nav actions; SKU table becomes stacked row presentation with visible field labels, no page-level horizontal scroll. Preserve semantic reading order; do not create duplicate focusable desktop/mobile controls.
- Font: existing LINE Seed Sans; body/input 1rem, helper .875rem, section heading 1.125rem, page heading 1.5rem; line-height 1.5. No fluid clamp headings.
- Spacing 4/8/12/16/24/32px. Section gap 24px; field gap 16px; interactive minimum 44px height. Inputs must not stretch vertically alongside textarea.
- Existing semantic CSS vars for surface, ink, muted, danger, warning, success and accent. One primary visual action per task. Badge includes text, never color alone.
- Focus outline 2px with offset; active controls visually distinct. Text contrast >=4.5:1, focus/non-text essential controls >=3:1; verify actual rendered colors.
- 150ms state transitions only; reduced-motion removes them. No smooth programmatic scrolling under reduced motion.
- Footer is `position: sticky; bottom: 0` in flow, has safe-area padding, and must not cover last field/focus target at 200% zoom/mobile keyboard.
- Dropdowns must remain custom branded and keyboard operable; if clipped use existing React portal capability, not z-index escalation inside clipped ancestors. Don't expand dependencies for this redesign.

## 7. Risks, tradeoffs and open questions

1. **UI versus actual security:** navigation is not authorization. Never move server session/role checks into a client component. Secret inventory remains its own API boundary.
2. **Fulfillment stale identity:** source exposes a credible wrong-target risk when typed ID changes; tests must establish actual behavior and fix client identity binding before SKU handoff. API authorization still required. Do not label system secure merely after UI tests.
3. **Worktree ownership:** existing branding/payment work overlaps globals.css and tests. Capture a baseline; review hunk ownership; no automatic whole-file stage.
4. **Scope discipline:** full backend redesign, order browser and aggregated group list are deferred. They need API discovery and separate scope, not guessed endpoints or mock production data.
5. **Form complexity:** collapsing everything can make a form harder. Keep core Thai/English content and price visible; hide infrequent metadata, not required work. Avoid multi-step wizard in first release because current create is atomic.
6. **Main-screen state:** in-memory navigation intentionally does not survive reload; introducing query routes/deep links is a later explicit requirement, not an unmentioned behavior.
7. **Sensitive drafts:** don't include fulfillment values in generic dirty snapshots, analytics, screenshots, URL or browser storage. Compare presence/change flags for secrets; clear on confirmed navigation.
8. **Independent saves:** uploaded images and inventory imports are committed operations; Cancel is not rollback. UI text must distinguish draft from already-saved action.
9. **Visual confirmation:** no live admin screenshot was inspected during planning; implementer must verify new hierarchy against actual rendered authenticated app before declaring it complete.
10. **Decisions for approval, not blockers to this plan:** default dark theme; products as landing task; no full order dashboard; desktop-first responsive; preserve all current capabilities. If user prefers light admin or daily order-first work, revise this plan before implementation rather than silently building another direction.
